# PPS 测试与性能排查记录

本文记录"测出 l4lb 单核转发上限"的完整过程：从端到端压测压不满，到搭建 memif 测试环境，再到排查并修复一系列测量和性能问题。复习时按"现象 → 分析 → 验证 → 解决 → 结果"来读。

最终结论：

| 指标 | 数值 |
| :--- | :--- |
| 端到端（wrk + nginx，VMware 虚拟网卡） | FULLNAT 12.6 万 QPS / 22.4 万 PPS，瓶颈在虚拟交换机 |
| 单转发核（memif，64B，丢包率 < 0.1%） | **400 万 PPS**，每次转发约 150 ns |
| 2 个转发核（同上） | **600 万 PPS**；尽力发送 950 万（受限于发包器） |
| 修复 rdtsc 问题后单核饱和转发量 | 约 290 万 → 约 650 万 PPS（约 2 倍） |

## 一、问题：端到端压测压不满 LB

### 现象

| 配置 | LB 转发 PPS | 转发核忙碌率 |
| :--- | ---: | ---: |
| 2 个转发核（`-l 1-3`） | 22.4 万 | 67% / 67% |
| 1 个转发核（`-l 1-2`） | 22.0 万 | 82% |

把转发核从 2 个减到 1 个，总 PPS 没变，只是 worker 更忙了。把 wrk 并发从 1000 加到 4000、线程从 4 加到 6，PPS 也不涨。

### 分析

- 总吞吐和转发核数量无关，说明瓶颈在 LB 之外。
- 在 client 上看 `top`：wrk 只用了约 2 个核（181%），`ksoftirqd/7` 占 47%，整机还有 66% 空闲。收包软中断集中在一个核上（虚拟网卡单队列、没开 RPS），wrk 线程再多也是在等这一个核收包。
- 宿主机层面：所有 VM 的 vmxnet3 和虚拟交换机都是宿主机 CPU 软件模拟的，l4lb 还固定占着几个忙轮询的 vCPU。

### 结论

wrk 测的是"client 协议栈 + 虚拟交换机 + LB + nginx"整条链路，LB 不是最慢的那一环，测不出它的上限。需要一个远快于 LB、并且绕开虚拟网卡的流量源。

## 二、方案：用 DPDK memif 直接给 LB 喂包

### 思路

`net_memif` 是 DPDK 自带的共享内存虚拟网卡，两个 DPDK 进程在同一台机器上直接交换报文，不经过网卡、虚拟交换机和内核。

```
memif_gen（发包器）                         l4lb（pipeline：1 收包核 + N 转发核）
  发包核：Client→VIP:9 的 64B UDP  ──memif──>  receiver → worker（FULLNAT 入站）→ 发给 RS
  收包核：发给 RS 的包原路回射      <──memif──
          （交换 MAC/IP/端口，模拟 RS 回包）──>  worker（FULLNAT 回程）→ 发给 Client
          发给 Client 的包计数后丢弃 <──memif──
```

每个 Client 包在 LB 上产生 2 次转发（入站 + 回程），完整走会话查找、FULLNAT 改写、校验和和 SNAT 回程这条路径。

### 为什么没直接用 testpmd

先试了 DPDK 自带的 testpmd：
- `txonly` 模式只发不收，l4lb 转回来的包把 memif ring 塞满，l4lb 出现大量 `tx_full`，测的是"对端不收包"而不是 LB 的能力。
- `flowgen` 模式把目的 IP、MAC 写死在代码里，没法指向 VIP。
- 两种模式都不能模拟 RS 回包，测不到 FULLNAT 回程。

所以写了一个专用发包器 `tests/perf/tools/memif_gen.c`（约 300 行）：
- 发包核按目标速率发送，速率可调；
- 收包核回射发给 RS 的包；
- 最后输出一行机器可读的结果，由 `tests/perf/memif_bench.sh` 解析。脚本会逐档调高速率，并用 l4lb 的 `counters` / `delta` 收集每一档的 PPS 和忙碌率。

## 三、排查过程：一共遇到 5 个问题

### 问题 1：包全部被丢，`drop_no_neigh` 暴涨

- **现象**：发包器显示回到 Client 的包是 0；l4lb 的 `drop_no_neigh` 达到 377 万。
- **分析**：`drop_no_neigh` 表示下一跳 MAC 没有解析到。测试配置的 netmask 是 /24（10.0.0.0/24），发包器用的客户端地址是 10.1.x.x，不在直连网段内，l4lb 就把回程包发往网关。配置里没有网关，memif 那头也没人回 ARP，所以回程包全部丢弃。
- **解决**：netmask 改成 255.0.0.0，让客户端变成直连地址。l4lb 对直连客户端会用首包的源 MAC 兜底（`resolve_client_mac`），回程就不需要 ARP。
- **收获**：先看丢包原因计数，再去猜原因。l4lb 把每种丢包原因分开计数，这次一眼就定位到了。

### 问题 2：转发数比发包数还多，"回来的包"却很少

- **现象**：发包 100 万/秒，LB 的 `fwd_in` 却有 178 万/秒；尽力发送时回到 Client 的包几乎为 0。
- **分析**：入站转发不可能比发包还多，说明有包被重复送进了 LB。原因有两个，叠加在一起：
  1. memif 不指定 MAC 时，每次启动都会随机生成一个。l4lb 的会话会记住首包的源 MAC，上一轮留下的会话会把回程包发给旧 MAC。
  2. 发包器的回射逻辑是"目的 MAC 不是我就回射"，于是发给旧 MAC 的回程包也被当成 RS 的包回射回去，在 LB 和发包器之间来回打转。
- **解决**：发包器固定使用 `mac=02:00:00:00:00:99`，并且只回射目的 MAC 是 RS（`02:00:00:00:00:1x`）的包。
- **收获**：计数之间要互相能对上（入站转发 ≤ 发包数，回程 ≤ 入站）。对不上时说明测试环境本身有问题，不能拿去下结论。

### 问题 3：2 个转发核时数据异常

- **现象**：2 个转发核时，回到 Client 的包比发出的包还多。
- **分析**：l4lb 的队列规划是 TX = worker 数 + 1（多出的一个给 master 线程），RX 向上取 2 的幂。2 个 worker 时是 4 RX / 3 TX，而发包器固定配了 2/2。memif 两端的 ring 数量不一致时，多出来的队列会访问到不该访问的 ring。
- **解决**：发包器新增 `--rxq` / `--txq` 参数，由脚本按 worker 数计算：发包器 RX = l4lb TX，发包器 TX = l4lb RX。
- **收获**：共享内存类接口要求两端严格对齐，这类问题不会报错，只会让数据悄悄出错。

### 问题 4（核心）：转发核负载才 70% 就开始丢包

- **现象**：单转发核在约 290 万 PPS 时就开始丢包（`rx_ring_full` 增长），但忙碌率只有 70% 左右，也就是说"还有 30% 空闲却处理不过来"，自相矛盾。
- **分析**：
  1. 用 `perf record -C 2`（只采样转发核）看热点：`worker_loop` 自身占了 45%，真正干活的 `handle`、`rte_hash_lookup_data` 加起来才 43%。循环本身不应该这么重。
  2. 用 `perf annotate` 看 `worker_loop` 的指令：约 98% 的样本落在两条 `shl $0x20,%rdx` 上。这两条指令紧跟在 `rdtsc` 后面，是把 rdtsc 返回的高 32 位拼成 64 位，样本记在下一条指令上，所以真正慢的是 `rdtsc` 本身。
  3. 写一个小程序在这台 VM 里实测：**每次 `rdtsc` 约 4 µs**，正常机器约 10 ns。VMware 拦截了 rdtsc，每次都要经过 hypervisor。`/proc/stat` 的 steal 为 0、调度等待为 0，排除了 vCPU 被抢占的可能。
  4. 原来的忙碌率统计在每轮循环开头和结尾各读一次 TSC（为了只统计"有包的轮次"）。一轮约 8 µs 花在读时钟上，读时钟本身就把 CPU 占满了；而且读时钟的时间有一部分没算进"忙"，所以忙碌率显示偏低。
- **解决**：`BusyMeter`（`include/common/stats.h`）改为每 256 轮循环才读一次 TSC：
  - 整个窗口都是空轮询时，用它校准一次空轮询的耗时（指数平均）；
  - 其他窗口：忙碌时间 = 窗口总耗时 − 空轮询次数 × 单次空轮询耗时。
  - 第一版只按"有包轮次的比例"估算，结果低负载时忙碌率只显示 1%~8%。原因是忙轮次比空轮次慢得多，按次数比例会严重低估。改成扣除空轮询耗时后，数值才合理。
- **结果**：单转发核饱和转发量从约 290 万提高到约 650 万 PPS，约 2 倍。单元测试和两种数据面模式下的全部功能测试都通过。
- **收获**：
  - 观测代码也有成本，而且在虚拟化环境里，"便宜"的指令可能非常贵。
  - 数据自相矛盾时（有空闲却丢包），优先怀疑测量本身。
  - 性能问题用 perf 先看函数级热点，再用 annotate 看到指令级。

### 问题 5：脚本算出的 PPS 偏低

- **现象**：同一档速率下，脚本算出的 PPS 比发包速率低约 7%（发 100 万/秒，算出 92.5 万）。
- **分析**：`delta` 的时间区间是"压测前读计数"到"压测后读计数"，中间还包含发包器启动 EAL、建立 memif 连接、退出的时间，分母偏大。
- **解决**：PPS 改用发包器自己统计的发送时长作分母；新增 `lb_loss` 列（LB 丢弃的包 ÷ LB 处理的包），按丢包率来判断拐点。

## 四、最终结果

`sudo tests/perf/memif_bench.sh`（1 个转发核），2026-10-09：

| 发包速率 | 往返成功 | LB 转发 PPS（入 + 回） | 收包核 | 转发核 | LB 丢包率 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.5M | 0.50M | 1.00M | 9.2% | 22.8% | 0.038% |
| 1.0M | 1.00M | 2.00M | 16.2% | 44.2% | 0.002% |
| **2.0M** | **2.00M** | **4.00M** | 25.5% | 70.9% | **0.030%** |
| 3.0M | 2.86M | 5.75M | 32.7% | 88.7% | 2.264% |
| 尽力（5.2M） | 2.91M | 6.21M | 29.0% | 94.0% | 27.098% |

- **无损转发**：丢包率 < 0.1% 时，单转发核 400 万 PPS。业界按"丢包率低于阈值时的最大转发速率"来衡量转发能力（RFC 2544 的思路），所以对外使用这个数字。
- **饱和**：转发核 94% 时约 620~670 万 PPS（多次测量的波动范围），再加流量只会丢包。
- **每次转发耗时**：94% ÷ 621 万 ≈ 150 ns（约 420 个 CPU 周期），包括会话查找、FULLNAT 改写和校验和。
- **收包核不是瓶颈**：转发核饱和时收包核只用了约 30%，一个收包核大约能喂饱 3 个转发核，说明 pipeline 的分工比例合理。
- **2 个转发核**：无损 600 万 PPS；尽力发送 950 万 PPS（丢包 0.8%），此时转发核才 81%，瓶颈是发包器（单核最多发约 480 万/秒）。

修复后的单核热点（`perf record -C 2`，发包 300 万/秒）：

| 函数 | 占比 | 说明 |
| :--- | ---: | :--- |
| `rte_hash_lookup_data` | 53% | 会话表查找 |
| `handle`（处理主流程，LTO 内联了 processor） | 23% | 分类、状态机、改写 |
| `eth_memif_tx` | 8% | memif 发包 |
| `memcmp` | 4% | 哈希 key 比较 |

**下一步优化方向**：会话查找占了一半时间，可以改成按批次查找（`rte_hash_lookup_bulk_data`），让多个包的内存访问并行，这是 DPVS 和 VPP 常用的做法。

## 五、端到端和单核数据怎么一起看

| | 端到端（wrk） | 单核能力（memif） |
| :--- | :--- | :--- |
| 测什么 | 整条链路的实际服务能力 | l4lb 代码本身的处理能力 |
| 1 个转发核 | 22 万 PPS，转发核 82%，压不满 | 400 万 PPS 无损 |
| 瓶颈 | client 内核收包、虚拟交换机 | 会话表查找 |
| 能不能和物理网卡比 | 不能（虚拟化） | 不能（不含网卡收发开销） |

两组数据回答的是不同的问题，简历和面试中要分开说。端到端数据是在修复 rdtsc 问题之前测的；修复后转发核的忙碌率会下降，QPS 预计变化不大，因为瓶颈在虚拟交换机。

## 六、复现

```bash
./build.sh
sudo tests/perf/memif_bench.sh                               # 1 个转发核
sudo WORKERS=2 tests/perf/memif_bench.sh                     # 2 个转发核
sudo RATES="2000000 3000000" DURATION=20 tests/perf/memif_bench.sh
```

- 运行前停掉其他 l4lb（会抢大页）；不碰 ens160，不影响压测拓扑。
- 结果在 `tests/perf/results/<时间>-memif/`：`summary.txt` 是汇总表，`delta_*.txt` 是每档的 LB 计数报告，`gen_*.txt` 是发包器的原始结果。
- 看热点：压测时另开终端执行 `perf record -F 2999 -C 2 -- sleep 5`，再执行 `perf report --no-children --sort symbol`。这台 VM 不支持硬件计数器（`perf stat` 的 cycles 显示 not supported），只能用采样。

## 七、面试问答

**Q：400 万 PPS 是怎么测的？可信吗？**
两个 DPDK 进程通过共享内存网卡对接。发包器发 64 字节 UDP、1 万条流，并把发往 RS 的包原路回射，所以每个包都完整走一遍 FULLNAT 的入站和回程。判断标准是发包器统计的"往返成功数"等于发包数、LB 的丢包率低于 0.1%，按这个条件取最大速率。各个计数要互相对得上（发包 ≥ 入站转发 ≥ 回程转发 = 往返成功），对不上的测试结果一律作废，问题 2、3 就是这样发现的。

**Q：为什么端到端只有 22 万，差了将近 20 倍？**
端到端时转发核负载只有 67~82%，网卡也没有丢包，LB 并没有被压满。慢在 client 的内核收包（软中断集中在一个核上）和虚拟交换机，这两部分都由宿主机 CPU 软件模拟。memif 绕开了这些环节，测到的才是 LB 本身的能力。

**Q：rdtsc 那个问题是怎么发现的？**
数据自相矛盾：转发核显示还有 30% 空闲，却已经开始丢包。perf 显示循环本身占了 45%，annotate 定位到 rdtsc 后面的指令，再写小程序实测出每次 rdtsc 约 4 µs，确认是 VMware 拦截了这条指令。修复方法是改为每 256 轮循环采样一次，并用空闲窗口校准空轮询的耗时，修复后单核饱和吞吐提升约 2 倍。

**Q：为什么不直接把忙碌率统计去掉？**
没有忙碌率就判断不了瓶颈在哪里，DPDK 忙轮询时 top 永远显示 100%。所以要保留这个功能，只是把它的成本降下来：现在每 256 轮循环只读一次时钟。满载时每轮都在处理包，256 轮的时间远大于一次 4 µs 的读时钟，开销可以忽略；空闲时多花的时间不影响转发。

**Q：每包 150 ns 花在哪里？还能怎么优化？**
一半以上花在会话表查找（`rte_hash_lookup_data`）上，其次是处理主流程和发包。可以改成批量查找，一次查 32 个 key，让多个包的内存访问重叠，减少 cache miss 的等待。
