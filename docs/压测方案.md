# 压测方案

## 一、目标

在 pipeline 模式（1 个 receiver + 2 个 worker，FULLNAT）下测一组可以写进简历的数据：

- 长连接 QPS（主指标）
- 短连接 CPS（新建连接能力，同时验证会话回收）
- 固定速率下的 p99 延迟
- 经过 LB 相对直连 RS 的损耗

数据必须能复现、能解释：标明环境，说清楚瓶颈在哪一侧。

## 二、为什么不能用现在的单机实验

`tests/perf/lab.sh` 把 loadgen、RS 和 LB 放在同一台 VM（12 vCPU）上，RS 走 ens33（e1000）。实测 13901 QPS、平均延迟 7ms，瓶颈在压测端和 RS 抢 CPU，不反映 LB 的能力。另外，同机打流量的数字写进简历也没有说服力。

所以需要 **压测客户端、LB、RS 分别在不同的 VM 上**。

## 三、拓扑

宿主机：笔记本 i7-13650HX（14 核 20 线程），VMware Workstation，所有 VM 接在同一个 vmnet（192.168.154.0/24）。

```
 client VM (wrk)                 LB VM（本机）                   RS VM × 2 (nginx)
 192.168.154.140   ──VIP .130──>  ens160 vmxnet3 / DPDK  ──LIP──>  192.168.154.132:80
                   <───────────   receiver lcore 1                 192.168.154.133:80
                                  worker lcore 2/3
                                  ens33 .142 管理口（SSH）
```

| VM | vCPU | 内存 | 软件 | 说明 |
|---|---|---|---|---|
| LB（现有） | 6~8 | 8G | l4lb | 只用 `-l 1-3`，其余核给 master、日志、控制线程和系统；现在 12 vCPU 可以降下来，减少宿主机超分 |
| client（新建） | 4~6 | 4G | wrk、wrk2 | IP 192.168.154.140 |
| RS1 / RS2 | 各 2~4 | 各 2G | nginx | IP .132 / .133，`config/lb.conf` 里已经是这两个地址（之前测试用过的话可以直接开机） |

- RS 用 nginx，不用我们自己的 `rs_server`。nginx 是业界通用的后端，数据更有说服力。
- 资源紧张时可以只开 1 台 RS VM，起两个 nginx 端口（:80 和 :8080），配置里写成两个 RS。
- 所有 VM 的 vCPU 总数尽量不超过宿主机线程数（20）。压测时关掉宿主机上的其他程序，插电源，并切到高性能模式。
- 简历上写环境时要注明是"VMware Workstation 虚拟化环境"。

## 四、准备工作

### 1. RS（两台都做）

```bash
dnf install -y nginx
systemctl disable --now firewalld          # 测试网络，或者只放行 80
cat > /etc/nginx/nginx.conf <<'EOF'
user nginx;
worker_processes auto;
worker_rlimit_nofile 200000;
events { worker_connections 65535; use epoll; multi_accept on; }
http {
    access_log off;
    keepalive_timeout 65;
    keepalive_requests 1000000;
    server {
        listen 80 reuseport backlog=65535;
        location / { return 200 "rs-$server_addr\n"; }
    }
}
EOF
sysctl -w net.core.somaxconn=65535 net.ipv4.tcp_max_syn_backlog=65535 \
          net.ipv4.tcp_tw_reuse=1
systemctl restart nginx && curl -s http://127.0.0.1/
```

### 2. 客户端

```bash
dnf install -y git gcc make openssl-devel zlib-devel
git clone https://github.com/wg/wrk.git && make -C wrk && cp wrk/wrk /usr/local/bin/
git clone https://github.com/giltene/wrk2.git && make -C wrk2 && cp wrk2/wrk /usr/local/bin/wrk2
sysctl -w net.ipv4.ip_local_port_range="1024 65000" net.ipv4.tcp_tw_reuse=1
ulimit -n 200000
# 把本仓库的 tests/perf/run_bench.sh 拷到客户端
```

### 3. LB

```bash
# 机器重启后先执行
sudo DPDK_NIC=ens160 scripts/setup_dpdk_env.sh up
# 压测配置：config/lb.conf 已经是 pipeline + RS .132/.133，压测时关掉终端输出
sed 's/^log_stderr = on/log_stderr = off/' config/lb.conf > /tmp/bench.conf
./build/l4lb -- --lb-config /tmp/bench.conf --check-config
sudo ./build/l4lb -l 1-3 -- --lb-config /tmp/bench.conf
scripts/l4lbctl.py services        # 两个 RS 都是 up
```

客户端上执行 `curl http://192.168.154.130/`，多请求几次，应该能看到 rs-132 和 rs-133 交替出现。

### 4. 观测点（已实现）

DPDK 是忙轮询，top 看到的 CPU 永远是 100%，没有参考价值。所以 l4lb 统计了每个线程的真实负载：

- **忙碌率**：receiver 和每个 worker 累计"有包可处理的轮次"花掉的 TSC 周期，再除以经过的时间（这也是 DPVS、VPP 的做法）。
- **网卡统计**：`rte_eth_stats_get` 的 `imissed`（网卡 RX 队列满丢弃）、`ierrors`、`rx_nombuf`。

查看方式：

```bash
tail -f /data/logs/l4/l4lb.log | grep -E "Rate:|Busy:|NIC:"   # 每 stats_interval 秒一次
scripts/l4lbctl.py rate        # 最近一个周期的速率、忙碌率、网卡丢包
scripts/l4lbctl.py stats -v    # 累计计数，含 NIC 一行和各线程 busy_ms
```

日志示例（单机 lab 压测时）：

```
=== Perf (last 3.0s) ===
Rate: rx 39.6k pps, tx 39.6k pps, fwd in 20.0k pps, fwd out 19.6k pps, new sess 3.1k /s, drops 0 /s
Busy: receiver 10.8% | worker0 24.1% 20.2kpps | worker1 23.1% 19.5kpps
NIC: rx 39.6k pps, tx 39.6k pps, imissed +0, ierrors +0, rx_nombuf +0 (total imissed 0)
```

退出时，Final Statistics 会打印整个运行期间的 `Avg busy` 和 `NIC imissed`。`stats_interval` 默认 10 秒；压测时可以改成 5 秒，在 wrk 运行期间多拿到几个采样点。

`run_bench.sh` 设置 `LB_HOST` 后，每一项测试结束都会 ssh 到 LB 上抓一次 `stats -v` 和 `rate`，保存为 `results/.../lb_stats_<测试项>.txt`。这样每个 QPS 数字都对应得上当时的忙碌率。LB 上的仓库路径默认是 `/root/l4-loadbalancer`，可以用 `LB_DIR` 修改。客户端需要能免密 ssh 到 LB：`ssh-copy-id root@192.168.154.142`。

## 五、测试矩阵

以下每项都跑 30 秒、重复 3 次，取均值（`run_bench.sh` 默认就是这样）。结果在客户端的 `tests/perf/results/<时间>-<标签>/` 目录下。

| # | 场景 | 命令（在客户端执行） | 作用 |
|---|---|---|---|
| 1 | 直连 RS 基线 | `tests/perf/run_bench.sh http://192.168.154.132/ direct` | 单台 RS 的上限，作为对照 |
| 2 | FULLNAT pipeline 1+2 | `LB_HOST=root@192.168.154.142 tests/perf/run_bench.sh http://192.168.154.130/ fullnat-pipe-1r2w` | **主数据**：长连接 QPS、短连接 CPS、p99 |
| 3 | FULLNAT pipeline 1+1 | LB 用 `-l 1-2` 启动，其余同 2，标签 `fullnat-pipe-1r1w` | 看加 worker 的收益 |
| 4 | DR pipeline 1+2 | 用 `config/lb_dr.conf`，RS 上按 README 配好 VIP 和 arp_ignore，标签 `dr-pipe-1r2w` | 对比 DR（回包不经过 LB） |

- `run_bench.sh` 会依次跑长连接（c=100/1000/2000）、短连接 `Connection: close`、wrk2 固定速率（20k/50k/80k）。
- 场景 2 跑完后，根据长连接最大 QPS，用 `RATES="<50%> <80%>"` 再跑一轮 wrk2，得到"在 X QPS 下 p99 为 Y ms"。
- 直连基线最好也测两台 RS 同时直连（客户端开两个 wrk 进程，各压一台），和经过 LB 的数字放在一起对比。

### 每轮都要检查（在 LB 上）

```bash
scripts/l4lbctl.py stats -v
```

- `Drops: none`。`rx_ring_full`、`tx_full`、`drop_table_full`、`drop_no_port` 都是 0。
- `redirect_out` 为 0，说明 receiver 分发正确。
- 两个 worker 的 `ring_in` 大致相当。
- wrk 输出 `Socket errors` 为 0，没有 `Non-2xx`。

只要有一项不满足，这轮数据就作废，先查原因。

## 六、如何判断瓶颈

| 现象 | 结论 | 下一步 |
|---|---|---|
| 经过 LB ≈ 直连，`Busy:` 里 worker 忙碌率低 | LB 不是瓶颈，RS 或客户端先到顶 | 加 RS（多开 nginx worker 或多一台 RS），或者给客户端加核 |
| worker 忙碌率接近 100%，`rx_ring_full` 增长 | worker 处理不过来 | 对比场景 3 和 2，看加 worker 是否线性提升 |
| receiver 忙碌率接近 100%，或者 `NIC: imissed +N` 增长 | 单 receiver 收包到顶 | 这就是 pipeline 模式的上限，如实记录 |
| 都不高，但 QPS 上不去 | vmxnet3 和虚拟交换机的限制 | 记录下来，说明是环境上限 |

## 七、简历怎么写

数据出来后，按下面的格式写，数字都替换成实测值：

> 基于 DPDK 实现 FULLNAT/DR 四层负载均衡，receiver + worker 流水线架构、per-worker 无锁会话表。在 VMware 虚拟化环境（vmxnet3，1 收包核 + 2 转发核）下，长连接 **X 万 QPS**，为直连 nginx 的 **Y%**；短连接 **Z 千 CPS**；在 W 万 QPS 下 p99 延迟 **N ms**，转发零丢包。

注意：
- 写清楚是虚拟化环境，不要拿去和 DPVS、Katran 在物理网卡上的 Mpps 比。
- 如果瓶颈在 RS，就写"LB 转发损耗小于 Y%，worker 忙碌率 Z%"，不要写成"LB 上限 X QPS"。
- 原始数据（`results/` 目录、`env.txt`、LB 的 stats）都留档，面试时被追问能拿得出来。
