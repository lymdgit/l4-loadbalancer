# 压测方案

## 一、目标

在 pipeline 模式（1 个 receiver + 2 个 worker，FULLNAT）下测一组可以写进简历的数据：

- 长连接 QPS（主指标）
- 短连接 CPS（新建连接能力，同时验证会话回收）
- 固定速率下的 p99 延迟
- 经过 LB 相对直连 RS 的损耗

数据必须能复现、能解释：标明环境，说清楚瓶颈在哪一侧。

## 二、为什么不能用现在的单机实验

`tests/perf/lab.sh` 把 loadgen、RS 和 LB 放在同一台 VM（12 vCPU）上，RS 走 ens33（e1000）。实测 13901 QPS、平均延迟 7ms，瓶颈在压测端和 RS 抢 CPU，不反映 LB 的能力。另外，同机打流量的数字写进简历也没有说服力。

所以需要 **压测客户端、LB、RS 分别在不同的 VM 上**。

## 三、拓扑

宿主机：笔记本 i7-13650HX（14 核 20 线程），VMware Workstation，所有 VM 接在同一个 vmnet（192.168.154.0/24）。

```
 client VM (wrk)                 LB VM（本机）                   RS VM (nginx)
 192.168.154.133   ──VIP .130──>  ens160 vmxnet3 / DPDK  ──LIP──>  192.168.154.140:80    "rs 1"
                   <───────────   receiver lcore 1                 192.168.154.140:8080  "rs 2"
                                  worker lcore 2/3
                                  LIP .131/.134/.135/.136
                                  ens33 .142 管理口（SSH）
```

| VM | vCPU | 内存 | 软件 | 说明 |
|---|---|---|---|---|
| LB（现有） | 6~8 | 8G | l4lb | 只用 `-l 1-3`，其余核给 master、日志、控制线程和系统；现在 12 vCPU 可以降下来，减少宿主机超分 |
| client | 4 | 4G | wrk、wrk2 | 192.168.154.133 |
| RS | 6 | 4G | nginx | 192.168.154.140，一个 nginx 监听 80 和 8080，模拟两个 RS |

- RS 用 nginx，不用我们自己的 `rs_server`。nginx 是业界通用的后端，数据更有说服力。
- 一台 nginx 开两个端口和两台 RS 的算力一样（`worker_processes auto` 已经用满所有核），关键是 RS 的总能力要高于 LB，所以给 RS 多分 vCPU。LB 的调度和健康检查按 `ip:port` 区分，两个端口就是两个独立的 RS。
- 代价：DR 模式只改 MAC、不改端口，RS 必须直接监听 VIP:80，单机两端口模拟不了两个 RS，DR 只能按单 RS 测（见第五节）。
- 所有 VM 的 vCPU 总数尽量不超过宿主机线程数（20）。压测时关掉宿主机上的其他程序，插电源，并切到高性能模式。
- 简历上写环境时要注明是"VMware Workstation 虚拟化环境"。

## 四、准备工作

### 0. 系统调优（三台都做）

把 `tests/perf/tune.sh` 拷到每台机器上，按角色执行：

```bash
sudo ./tune.sh client apply    # client .133
sudo ./tune.sh rs apply        # RS .140（同时放行 80/8080）
sudo ./tune.sh lb apply        # LB .142（另外检查大页和 DPDK 网卡）
ulimit -n 1048576              # 在之后启动 wrk / nginx / l4lb 的 shell 里执行
```

`show` 只查看当前值，`revert` 恢复。sysctl 只改运行时的值，重启后会自动恢复。下面第 1、2 节里的 sysctl 和 ulimit 命令已经包含在脚本里，不用再单独执行。


### 1. RS（192.168.154.140，nginx 源码安装在 /usr/local/nginx）

`/usr/local/nginx/conf/nginx.conf` 整个替换为：

```nginx
worker_processes      auto;          # 每个 vCPU 一个 worker
worker_cpu_affinity   auto;          # worker 绑核
worker_rlimit_nofile  200000;
error_log  logs/error.log  warn;

events {
    worker_connections  65535;
    use epoll;
    multi_accept on;
}

http {
    access_log     off;              # 压测时写访问日志会先把磁盘打满
    server_tokens  off;
    default_type   text/plain;
    tcp_nodelay    on;
    keepalive_timeout   65;
    keepalive_requests  1000000;     # 默认 1000 次后断开，会让长连接测试混入建连

    # 两个端口模拟两个 RS，返回内容不同，curl VIP 时能看出分到了哪个
    # 不读文件，直接返回小响应：测的是转发，不是磁盘和 sendfile
    server {
        listen 80 reuseport backlog=65535;
        location / { return 200 "rs 1 $server_addr\n"; }
    }
    server {
        listen 8080 reuseport backlog=65535;
        location / { return 200 "rs 2 $server_addr\n"; }
    }
}
```

内核参数与启动：

```bash
cat > /etc/sysctl.d/90-bench.conf <<'EOF'
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.core.netdev_max_backlog = 65535
net.ipv4.tcp_max_tw_buckets = 2000000
EOF
sysctl --system
ulimit -n 200000
systemctl disable --now firewalld 2>/dev/null; ufw disable 2>/dev/null   # 或只放行 80
/usr/local/nginx/sbin/nginx -t
/usr/local/nginx/sbin/nginx -s reload 2>/dev/null || /usr/local/nginx/sbin/nginx
curl -s http://127.0.0.1/ http://127.0.0.1:8080/    # rs 1 ... / rs 2 ...
```

### 2. 客户端（192.168.154.133，4 vCPU）

用 wrk：它是事件驱动的，一个线程能撑几万到十几万 QPS，4 核足够把 nginx 压满。ab 是单线程的，客户端会先到顶；wrk2 只用来测固定速率下的尾延迟。

```bash
# Ubuntu: apt install -y git build-essential libssl-dev zlib1g-dev
# RHEL 系: dnf install -y git gcc make openssl-devel zlib-devel
git clone https://github.com/wg/wrk.git && make -C wrk && cp wrk/wrk /usr/local/bin/
git clone https://github.com/giltene/wrk2.git && make -C wrk2 && cp wrk2/wrk /usr/local/bin/wrk2
sysctl -w net.ipv4.ip_local_port_range="1024 65000" net.ipv4.tcp_tw_reuse=1
ulimit -n 200000
ssh-copy-id root@192.168.154.142     # run_bench.sh 每项结束 ssh 到 LB 抓统计
scp root@192.168.154.142:/root/l4-loadbalancer/tests/perf/run_bench.sh .
```

4 核客户端的参数：`THREADS=4`（每个核一个线程）；并发 `CONNS="100 400 1000"`，超过 1000 以后在 4 核上主要是排队，QPS 不会再涨，只会拉高延迟。

```bash
THREADS=4 CONNS="100 400 1000" ./run_bench.sh http://192.168.154.140/ direct
```

### 3. LB

```bash
# 机器重启后先执行
sudo DPDK_NIC=ens160 scripts/setup_dpdk_env.sh up
# 压测配置 config/bench.conf：pipeline + RS 140:80 / 140:8080 + 4 个 LIP，
# 不输出终端，统计间隔 5 秒
./build/l4lb -- --lb-config config/bench.conf --check-config
sudo ./build/l4lb -l 1-3 -- --lb-config config/bench.conf
scripts/l4lbctl.py services        # 两个 RS 都是 up
```

客户端上执行 `for i in 1 2 3 4; do curl -s http://192.168.154.130/; done`，应该能看到 `rs 1` 和 `rs 2` 交替出现。

### 4. 观测点（已实现）

DPDK 是忙轮询，top 看到的 CPU 永远是 100%，没有参考价值。所以 l4lb 统计了每个线程的真实负载：

- **忙碌率**：receiver 和每个 worker 累计"有包可处理的轮次"花掉的 TSC 周期，再除以经过的时间（这也是 DPVS、VPP 的做法）。
- **网卡统计**：`rte_eth_stats_get` 的 `imissed`（网卡 RX 队列满丢弃）、`ierrors`、`rx_nombuf`。

查看方式：

```bash
tail -f /data/logs/l4/l4lb.log | grep -E "Rate:|Busy:|NIC:"   # 每 stats_interval 秒一次
scripts/l4lbctl.py rate        # 最近一个周期的速率、忙碌率、网卡丢包
scripts/l4lbctl.py stats -v    # 累计计数，含 NIC 一行和各线程 busy_ms
```

日志示例（单机 lab 压测时）：

```
=== Perf (last 3.0s) ===
Rate: rx 39.6k pps, tx 39.6k pps, fwd in 20.0k pps, fwd out 19.6k pps, new sess 3.1k /s, drops 0 /s
Busy: receiver 10.8% | worker0 24.1% 20.2kpps | worker1 23.1% 19.5kpps
NIC: rx 39.6k pps, tx 39.6k pps, imissed +0, ierrors +0, rx_nombuf +0 (total imissed 0)
```

退出时，Final Statistics 会打印整个运行期间的 `Avg busy` 和 `NIC imissed`。`stats_interval` 默认 10 秒；压测时可以改成 5 秒，在 wrk 运行期间多拿到几个采样点。

`run_bench.sh` 设置 `LB_HOST` 后，每一项测试结束都会 ssh 到 LB 上抓一次 `stats -v` 和 `rate`，保存为 `results/.../lb_stats_<测试项>.txt`。这样每个 QPS 数字都对应得上当时的忙碌率。LB 上的仓库路径默认是 `/root/l4-loadbalancer`，可以用 `LB_DIR` 修改。客户端需要能免密 ssh 到 LB：`ssh-copy-id root@192.168.154.142`。

## 五、测试矩阵

以下每项都跑 30 秒、重复 3 次，取均值（`run_bench.sh` 默认就是这样）。结果在客户端的 `tests/perf/results/<时间>-<标签>/` 目录下。

| # | 场景 | 命令（在客户端执行） | 作用 |
|---|---|---|---|
| 1 | 直连 RS 基线 | `THREADS=4 CONNS="100 400 1000" ./run_bench.sh http://192.168.154.140/ direct` | nginx 整机的上限（两个端口共享同一批 worker，压一个端口就是整机上限），作为对照 |
| 2 | FULLNAT pipeline 1+2 | `THREADS=4 CONNS="100 400 1000" LB_HOST=root@192.168.154.142 ./run_bench.sh http://192.168.154.130/ fullnat-pipe-1r2w` | **主数据**：长连接 QPS、短连接 CPS、p99 |
| 3 | FULLNAT pipeline 1+1 | LB 用 `-l 1-2` 启动，其余同 2，标签 `fullnat-pipe-1r1w` | 看加 worker 的收益 |
| 4 | DR pipeline 1+2 | 见第十节，用 `config/bench_dr.conf`，标签 `dr-pipe-1r2w` | 对比 DR（回包不经过 LB）；单 RS |

- `run_bench.sh` 会依次跑长连接（上面的 CONNS）、短连接 `Connection: close`、wrk2 固定速率（20k/50k/80k）。
- 场景 2 跑完后，根据长连接最大 QPS，用 `RATES="<50%> <80%>"` 再跑一轮 wrk2，得到"在 X QPS 下 p99 为 Y ms"。

### 手动用 wrk 时怎么拿 PPS

```bash
# LB 上，压测前
scripts/l4lbctl.py counters > /tmp/before.txt
# client 上
wrk -t4 -c1000 -d60s --latency http://192.168.154.130/
# LB 上，压测后
scripts/l4lbctl.py delta /tmp/before.txt
```

`total fwd` 那一行就是 LB 的转发 PPS 和 bps（FULLNAT 为 in + out），`busy:` 是这段时间内各线程的忙碌率，详见 `docs/pps方案.md`。

### 每轮都要检查（在 LB 上）

```bash
scripts/l4lbctl.py stats -v
```

- `Drops: none`。`rx_ring_full`、`tx_full`、`drop_table_full`、`drop_no_port` 都是 0。
- `redirect_out` 为 0，说明 receiver 分发正确。
- 两个 worker 的 `ring_in` 大致相当。
- wrk 输出 `Socket errors` 为 0，没有 `Non-2xx`。

只要有一项不满足，这轮数据就作废，先查原因。

## 六、如何判断瓶颈

| 现象 | 结论 | 下一步 |
|---|---|---|
| 经过 LB ≈ 直连，`Busy:` 里 worker 忙碌率低 | LB 不是瓶颈，RS 或客户端先到顶 | 给 RS VM 加 vCPU，或者给客户端加核 |
| worker 忙碌率接近 100%，`rx_ring_full` 增长 | worker 处理不过来 | 对比场景 3 和 2，看加 worker 是否线性提升 |
| receiver 忙碌率接近 100%，或者 `NIC: imissed +N` 增长 | 单 receiver 收包到顶 | 这就是 pipeline 模式的上限，如实记录 |
| 都不高，但 QPS 上不去 | vmxnet3 和虚拟交换机的限制 | 记录下来，说明是环境上限 |

## 七、实测结果（2026-10-09）

LB `-l 1-3`（pipeline 1+2），`wrk -t4 -c1000 -d60s`，长连接：

| 场景 | QPS | p99 | LB 转发 PPS | 转发核忙碌率 | 丢包 |
| :--- | ---: | ---: | ---: | ---: | :---: |
| 直连 nginx | 161,674 | 89.50 ms | – | – | – |
| FULLNAT | 126,145 | 48.88 ms | 223.9k（in 111.6k + out 112.3k） | 67% | 1（软件丢包，网卡和 ring 为 0） |
| DR | 133,090 | 36.74 ms | 121.1k（只有入向） | 33% | 0 |

按第六节的判断：转发核负载 67%、`imissed` 为 0，LB 还有余量，QPS 的差距主要来自虚拟交换机（FULLNAT 每个请求比直连多经过两次，DR 多一次）。数据也同步到了根目录 README 第六节。

## 八、简历怎么写

数据出来后，按下面的格式写，数字都替换成实测值：

> 基于 DPDK 实现 FULLNAT/DR 四层负载均衡，receiver + worker 流水线架构、per-worker 无锁会话表。在 VMware 虚拟化环境（vmxnet3，1 收包核 + 2 转发核）下，后端 1 台 nginx（2 个服务端口），长连接 **X 万 QPS**，为直连 nginx 的 **Y%**；短连接 **Z 千 CPS**；在 W 万 QPS 下 p99 延迟 **N ms**，转发零丢包。

注意：
- 写清楚是虚拟化环境，不要拿去和 DPVS、Katran 在物理网卡上的 Mpps 比。
- 如果瓶颈在 RS，就写"LB 转发损耗小于 Y%，worker 忙碌率 Z%"，不要写成"LB 上限 X QPS"。
- 原始数据（`results/` 目录、`env.txt`、LB 的 stats）都留档，面试时被追问能拿得出来。

## 十、DR 模式

### 1. 和 FULLNAT 的区别

```
client ──请求──> LB ──(只改目的 MAC)──> RS
   ^                                     │
   └──────────── 回包直接返回 ───────────┘
```

- LB 只改目的 MAC，IP 和端口都不变。RS 收到的目的地址仍然是 VIP，所以 RS 的 lo 上必须配上 VIP，并且不能对外应答 VIP 的 ARP。
- 回包从 RS 直接发给 client，不经过 LB。
- DR 不改端口，RS 端口必须和 VIP 端口相同。RS 按 MAC 区分，同一台 VM 只有一个 MAC，所以一台 nginx 只能当 **一个** RS（`140:8080` 在 DR 下用不了）。这不影响测 LB 的转发能力。
- 不需要 LIP。健康检查仍从 `hc_src`（.131）发出，RS 的 SYN-ACK 回到 `hc_src`，由 LB 收下，所以健康检查照常可用。

### 2. 步骤

RS（.140）：
```bash
scp root@192.168.154.142:/root/l4-loadbalancer/tests/perf/{dr_rs.sh,nic_delta.sh} .
sudo ./dr_rs.sh up        # 先改 arp_ignore=1 / arp_announce=2，再在 lo 上加 VIP
sudo ./dr_rs.sh status    # 显示 "DR ready"
```

LB：
```bash
sudo ./build/l4lb -l 1-3 -- --lb-config config/bench_dr.conf
scripts/l4lbctl.py services          # rs 1 192.168.154.140:80 ... up
```

client（.133）：
```bash
ip neigh flush 192.168.154.130       # 清掉 VIP 可能残留的 ARP（之前的测试或 dr_rs.sh up 的过程）
ip neigh show 192.168.154.130        # 访问一次后，MAC 应该是 LB 的 ens160（00:0c:29:53:a7:09），不是 RS 的
curl http://192.168.154.130/         # rs 1 192.168.154.130（nginx 的 $server_addr 是 VIP，说明走的是 DR）
```

如果 `ip neigh` 里 VIP 的 MAC 是 RS 的，说明 client 绕过了 LB 直接访问 RS，测出来的就是直连数据。这时检查 RS 上的 `dr_rs.sh status`，然后在 client 上重新 flush。

### 3. 测试与 PPS

```bash
# LB 上
scripts/l4lbctl.py counters > /tmp/before.txt
# RS 上（统计回程）
./nic_delta.sh                       # Ctrl+C 结束
# client 上
wrk -t4 -c1000 -d60s --latency http://192.168.154.130/
wrk -t4 -c400  -d30s --latency -H "Connection: close" http://192.168.154.130/   # 短连接
# LB 上
scripts/l4lbctl.py delta /tmp/before.txt
```

或者在 client 上一次跑完整套：
```bash
THREADS=4 CONNS="100 400 1000" LB_HOST=root@192.168.154.142 ./run_bench.sh http://192.168.154.130/ dr-pipe-1r2w
```

PPS 的口径：

| 数据 | 从哪里拿 | 说明 |
|---|---|---|
| LB 转发 PPS | LB `delta` 的 `fwd in`（`total fwd` 与它相等，`fwd out` 为 0） | DR 的 LB 只处理入向；长连接下大约是 QPS 的 1~2 倍（请求包 + client 对响应的 ACK） |
| 回程 PPS | RS 上 `nic_delta.sh` 的 `tx` | 回包不经过 LB，RS 出向就是回程；可以用来证明 LB 确实没有处理回包 |
| QPS / 延迟 | wrk | 同 FULLNAT |

**不要直接比较 DR 和 FULLNAT 的 PPS 数字**：FULLNAT 的 `total fwd` 包含两个方向，DR 只有一个方向。可以比较的是"同样的 QPS 下 LB 的忙碌率"，DR 应该明显更低。

### 4. 预期

- QPS 接近直连 nginx：流量路径是 client→LB→RS→client，穿过 3 次虚拟交换机（直连 2 次，FULLNAT 4 次）。
- LB 忙碌率明显低于 FULLNAT。
- 短连接时，LB 只看得到 client 发的 FIN，看不到 RS 发的 FIN，会话会在 FIN_WAIT 停留 `tcp_fin_timeout`（10 秒）后回收。活跃会话数会比 FULLNAT 高，但离 `max_sessions` 很远，不影响测试。

### 5. 还原

测完 DR 回到 FULLNAT 之前，一定要还原 RS，否则 RS 的 lo 上一直有 VIP，FULLNAT 测试时 RS 会把发给 VIP 的包当作本机包：

```bash
sudo ./dr_rs.sh down       # RS 上：删除 lo 上的 VIP，恢复 arp 参数
ip neigh flush 192.168.154.130   # client 上
```

`dr_rs.sh` 的修改都是运行时设置，RS 重启后也会自动失效。

## 十一、单核转发能力（memif，排除网卡和虚拟化开销）

> 完整的排查过程（5 个问题的现象、分析和解决）见 `docs/PPS测试与性能排查.md`。

### 1. 为什么要单独测

wrk 测的是整条链路：client 协议栈、虚拟交换机、vmxnet3、LB、nginx。实测 1 个转发核在约 22 万 pps 时负载 82%，再加 wrk 并发也压不上去，因为 client 内核收包软中断集中在一个核上、宿主机的虚拟交换机也到顶了，LB 没被压满。

要测 LB 本身的上限，需要一个远快于 LB 的流量源，并且绕开虚拟网卡。

### 2. 方法

```
memif_gen（发包器，lcore 8-10）           l4lb（pipeline，lcore 1 收包 + 2.. 转发）
  发包核：Client→VIP:9 的 64B UDP  ──net_memif（共享内存）──>  receiver → worker
          10000 条流，按目标速率发送                              FULLNAT 改写，发给 RS
  收包核：发给 RS 的包原路回射      <──────────────────────────
          （交换 MAC/IP/端口，相当于 RS 回包）       ──────────>  回程 FULLNAT，发给 Client
          发给 Client 的包计数后丢弃  <──────────────────────────
```

- `net_memif` 是 DPDK 自带的基于共享内存的虚拟网卡，两个进程在同一台机器上直接交换报文，不经过网卡、虚拟交换机和内核。
- 每个 Client 包在 l4lb 上产生 2 次转发（入站 + 回程），完整走 FULLNAT 的会话查找、改写、校验和、SNAT 回程路径。
- 发包器：`tests/perf/tools/memif_gen.c`；脚本：`tests/perf/memif_bench.sh`（自动编译发包器、启动 l4lb、逐档测速、用 `counters`/`delta` 收集结果）。

```bash
sudo tests/perf/memif_bench.sh                         # 1 个转发核
sudo WORKERS=2 tests/perf/memif_bench.sh               # 2 个转发核
sudo RATES="2000000 3000000" DURATION=20 tests/perf/memif_bench.sh
```

运行前停掉其他 l4lb（会抢大页）；不碰 ens160，不影响压测拓扑。结果在 `tests/perf/results/<时间>-memif/`。

解读：
- **单转发核：丢包率 < 0.1% 时约 400 万 PPS（64B），饱和时约 670 万 PPS**。超过 2.5M 发包速率后丢包开始上升（`rx_ring_full`，worker 来不及处理），转发核忙碌率 94% 时转发量不再增加。
- **2 个转发核：丢包率 < 0.1% 时约 600 万 PPS，尽力发送下约 950 万 PPS、丢包 0.8%**。2 个核时转发核还没满（81%），这时的瓶颈是发包器（单核发包最多约 480 万/秒），不是 LB。
- 和 wrk 的端到端结果相比：同样 1 个转发核，wrk 下只有约 22 万 PPS，memif 下 400 万以上。差距在虚拟网卡和虚拟交换机，不在 l4lb 的处理逻辑。
- 单核热点（`perf record -C 2`，3M 发包速率）：`rte_hash_lookup_data` 约 53%（会话表查找）、`handle` / 处理主流程约 23%、`eth_memif_tx` 约 8%。下一步优化方向是会话查找（批量查找 `rte_hash_lookup_bulk_data`、减少 key 比较）。

注意：
- 这是"l4lb 代码本身"的处理能力，不含真实网卡的收发开销，不能和物理网卡上的端到端结果直接对比。简历上要和 wrk 的端到端数据分开写，并注明测法。
- 10000 条流在测试开始时建立，之后都是已有会话的转发，测的是转发路径，不是新建连接速度。

### 4. 测量过程中发现并修复的问题

最初的测试里转发核忙碌率只有 70% 左右就开始丢包，`perf annotate` 显示近一半的时间花在 `worker_loop` 里的 `rdtsc` 指令上。在 VMware 下 `rdtsc` 被 hypervisor 拦截（本机实测每次约 4 µs，正常约 10 ns），而忙碌率统计每轮循环要读两次 TSC，读时钟本身占满了 CPU。

修复：`BusyMeter`（`include/common/stats.h`）改为每 256 轮循环读一次 TSC，用纯空轮询的窗口校准一次空轮询的耗时，再从窗口总时间里扣除。修复后单转发核的饱和转发量从约 290 万提高到约 670 万 PPS。这个问题也会影响 vmxnet3 下的端到端测试（每包 6 µs 里有一部分就是读时钟），之后的 wrk 数据需要用修复后的版本重测。
