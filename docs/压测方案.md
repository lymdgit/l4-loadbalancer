# 压测方案（memif）

## 一、目标

测出 **l4lb 代码本身**的转发能力，即在不含物理网卡、虚拟交换机和内核协议栈开销的情况下，一个转发核每秒能处理多少个 64 字节报文。

- 主指标：丢包率低于 0.1% 时的最大转发 PPS（RFC 2544 的思路）
- 辅助指标：转发核 / 收包核忙碌率、每包耗时、加 worker 后的线性度
- 数据必须能复现、能解释：写明环境，说清楚瓶颈在哪一侧

## 二、为什么用 memif

早期试过端到端方案（独立 client VM 用 wrk 压 nginx，LB 在另一台 VM），结论是**压不满 LB**：1 个转发核在约 22 万 pps 时忙碌率只有 82%，网卡没有丢包，再加并发 QPS 也上不去。瓶颈在客户端内核收包软中断和宿主机的虚拟交换机（都由宿主 CPU 软件模拟），不在 l4lb。

要测 LB 的上限，需要一个**远快于 LB 的流量源**，并且**绕开虚拟网卡**。在虚拟机环境里可选的手段只有：

| 方案 | 问题 |
| :--- | :--- |
| 物理打流仪 / TRex | 需要独占网卡和独立机器，虚拟机里不可行 |
| 多开 VM 用 wrk 打 | 仍走 vSwitch，上限还是几十万 pps |
| **DPDK `net_memif`** | 两个进程共享内存直连，单核发包可达约 480 万 pps，满足要求 |

`net_memif` 是 DPDK 自带的基于共享内存的虚拟网卡：控制面用 unix socket 握手（协商队列、ring 地址、MAC），数据面在共享内存的 ring 上直接交换描述符，不经过网卡、vSwitch 和内核。对 l4lb 而言它就是一块普通网卡，`rte_eth_rx_burst` / `rte_eth_tx_burst` 照旧。

没有直接用 testpmd 的原因：`txonly` 只发不收，回程包把 ring 塞满；`flowgen` 写死了目的 IP/MAC；两者都不能模拟 RS 回包，测不到 FULLNAT 回程。所以写了一个专用发包器 `tests/perf/tools/memif_gen.c`。

## 三、拓扑

```
memif_gen（发包器，lcore 8-10）              l4lb（pipeline，lcore 1 收包 + 2.. 转发）
  发包核：Client → VIP:9 的 64B UDP ──net_memif──> receiver → worker（FULLNAT 入站）→ 发给 RS
          10000 条流，按目标速率发送
  收包核：发给 RS 的包原路回射     <──────────────
          （交换 MAC/IP/端口，相当于 RS 回包）────> worker（FULLNAT 回程）→ 发给 Client
          发给 Client 的包计数后丢弃 <──────────────
```

- 每个 Client 包在 LB 上产生 2 次转发（入站 + 回程），完整走会话查找、FULLNAT 改写、校验和、SNAT 回程路径。
- 发包器与 l4lb 用同一个 unix socket 配对（l4lb `role=server`，发包器 `role=client`），两端 lcore、大页完全在本机。
- MAC 固定：l4lb `02:00:00:00:00:01`，发包器 `02:00:00:00:00:99`，RS 的 MAC 为 `02:00:00:00:00:1x`（发包器按这个前缀识别"该回射的包"）。会话会记住首包源 MAC，所以每次运行必须用同一个 MAC，否则上一轮的会话会把包发给旧 MAC。

## 四、准备工作

1. 编译 l4lb：`./build.sh`
2. 配置大页（`scripts/setup_dpdk_env.sh up` 或手工 `echo 1024 > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages`）。memif 用 `--no-pci` 启动，不需要绑定物理网卡。
3. 停掉其它 l4lb / memif_gen：都是忙轮询，抢同一个 lcore 会让两边都只剩一半吞吐且大量丢包。
4. 规划 lcore：pipeline 模式至少 `1 + WORKERS` 个核给 l4lb，另需 3 个核给发包器（main + 发包 + 收包），互不重叠。

## 五、怎么跑

```bash
sudo tests/perf/memif_bench.sh                         # 1 个转发核
sudo WORKERS=2 tests/perf/memif_bench.sh               # 2 个转发核
sudo RATES="2000000 3000000" DURATION=20 tests/perf/memif_bench.sh
```

脚本自动完成：编译发包器 → 生成临时 lb 配置（UDP 服务、静态 RS MAC、关闭健康检查）→ 启动 l4lb（pipeline + memif server）→ 按 `RATES` 逐档启动发包器 → 每档前后用 `l4lbctl.py counters` / `delta` 取 l4lb 计数 → 汇总到 `tests/perf/results/<时间>-memif/summary.txt`。

参数（`WORKERS`、`RATES`、`DURATION`、`FLOWS`、`SIZE`、`REFLECT`、`LB_LCORES`、`GEN_LCORES`）和输出列的含义见 `tests/perf/README.md`。

## 六、结果怎么看

每档至少检查三件事：

1. **计数互相对得上**：`gen_tx ≥ fwd_in ≥ fwd_out = gen_back`。入站转发不可能多于发包数，回程不可能多于入站；对不上说明测试环境有问题（会话串了、包在环、两端队列数不匹配），该轮作废。
2. **按丢包率取能力值**：`lb_loss < 0.1%` 时的最大转发速率才是"无损转发能力"；`lb_loss` 包含 `rx_ring_full` 和 `tx_full`。
3. **转发核忙碌率**：接近 100% 说明到顶；远低于 100% 而转发量不再上涨，说明瓶颈在发包器。收包核忙碌率过高则是 receiver 成为上限（pipeline 模式的固有上限）。

## 七、实测结果（2026-10-09，12 vCPU VM，i7-13650HX）

1 个转发核（`-l 1-2`）：

| 发包速率 | 往返成功 | LB 转发 PPS（入 + 回） | 收包核 | 转发核 | LB 丢包率 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1.0M | 1.00M | 2.00M | 14.8% | 41.4% | 0.009% |
| 1.5M | 1.50M | 3.00M | 19.9% | 56.0% | 0.013% |
| **2.0M** | **2.00M** | **4.00M** | 24.4% | 65.9% | **0.025%** |
| 2.5M | 2.47M | 4.95M | 29.8% | 77.1% | 0.570% |
| 3.0M | 2.93M | 5.86M | 31.1% | 84.2% | 1.223% |
| 3.5M | 3.27M | 6.58M | 30.9% | 90.0% | 3.377% |
| 4.0M | 3.28M | 6.69M | 32.8% | 93.7% | 9.696% |

2 个转发核（`-l 1-3`）：

| 发包速率 | 往返成功 | LB 转发 PPS（入 + 回） | 收包核 | 转发核 | LB 丢包率 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2.0M | 2.00M | 4.00M | 28.3% | 49.4% / 48.3% | 0.012% |
| **3.0M** | **3.00M** | **5.99M** | 36.9% | 61.8% / 61.3% | **0.032%** |
| 4.0M | 3.98M | 7.97M | 47.1% | 73.7% / 73.1% | 0.191% |
| 尽力（4.8M） | 4.72M | 9.46M | 55.6% | 81.6% / 80.9% | 0.823% |

解读：

- **单转发核：丢包率 < 0.1% 时约 400 万 PPS（64B），饱和时约 670 万 PPS**。超过 2.5M 发包速率后 `rx_ring_full` 增长，转发量在转发核忙碌率 94% 时不再增加。
- **2 个转发核：丢包率 < 0.1% 时约 600 万 PPS，尽力发送约 950 万 PPS（丢包 0.8%）**。此时转发核只有 81%，瓶颈是发包器（单核发包上限约 480 万/秒），不是 l4lb。
- 单核热点（`perf record -C 2`，3M 发包速率）：`rte_hash_lookup_data` 约 53%（会话表查找）、`handle` / 主处理流程约 23%、`eth_memif_tx` 约 8%。每包约 150 ns，下一步优化方向是批量会话查找。

## 八、测量过程中发现并修复的问题

| # | 现象 | 原因 / 处理 |
| :--- | :--- | :--- |
| 1 | `drop_no_neigh` 暴涨、回程为 0 | 客户端地址不在直连网段，回程包被发往网关；netmask 改为 `/8` 后走直连，用首包源 MAC 兜底 |
| 2 | 入站转发数大于发包数，回程却很少 | memif MAC 随机 + 回射条件过宽，包在 LB 和发包器之间打转；固定 MAC，只回射目的 MAC 属于 RS 的包 |
| 3 | 2 个转发核时数据异常 | 两端队列数不匹配（l4lb 4 RX / 3 TX，发包器固定 2/2）；新增 `--rxq` / `--txq`，由脚本按 worker 数计算 |
| 4 | 转发核忙碌率 70% 就丢包 | VMware 拦截 `rdtsc`（每次约 4 µs），忙碌率统计每轮读两次时钟；`BusyMeter` 改为每 256 轮采样一次 |
| 5 | 脚本算出的 PPS 偏低约 7% | 分母包含了发包器启动和连接建立的耗时；改用发包器自己统计的发送时长 |

问题 4 修复后，单转发核饱和转发量从约 290 万提升到约 670 万 PPS。完整的现象 → 分析 → 验证过程见 `docs/PPS测试与性能排查.md`。

## 九、简历怎么写

> 基于 DPDK 实现 FULLNAT/DR 四层负载均衡，receiver + worker 流水线架构、per-worker 无锁会话表。用 DPDK `net_memif` 共享内存网卡搭建单机压测环境（64B 小包、1 万条会话、每包走完整入站 + 回程），**单转发核无损转发 400 万 PPS、饱和约 670 万 PPS，2 核约 600 万 PPS**，每包约 150 ns，丢包率 < 0.1%。

注意：

- 必须注明测法（memif、不含物理网卡收发开销），**不要**和物理网卡上的端到端 Mpps 或 DPVS、Katran 的公开数据直接比较。
- 数据要写清楚判据：丢包率低于 0.1% 时的最大速率，而不是"尽力发送"的数字。
- 原始数据在 `tests/perf/results/`，面试被追问时能拿得出来。

## 十、限制

- 不含真实网卡的收发开销，也不含物理链路和交换机，测的是 l4lb 代码本身。
- memif 默认 copy 模式（两端各自 `--file-prefix`），每包有一次内存拷贝，不影响横向对比，但绝对数字略低于 zero-copy。
- 会话在测试开始时建立，之后都是已有会话的转发，**不测新建连接速度**（CPS）。
- 发包器单核约 480 万 pps，测 2 核以上时需要多核发包或降低 `WORKERS` 的判定标准，否则会把"发包器上限"误读成"LB 上限"。
- 测试要独占 lcore 和大页，不能与其它 DPDK 进程同时运行。
